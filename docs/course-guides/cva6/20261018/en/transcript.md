# Introducing CVA6: Architecture, Uses and Engineering Evidence

## 1. CVA6: configurable RISC-V processor IP for different systems (s01)

If you want a RISC-V processor design that you can study, modify and integrate into a system, CVA6 offers a concrete starting point. It is a configurable open-source processor-IP family, with 32-bit and 64-bit variants sharing SystemVerilog source. IP means a reusable hardware design: the core executes instructions, while memory, peripherals and software complete the system. We will see embedded control, Linux hosting and accelerator management. Those uses are possibilities supported by specific configurations and platforms. They are not guarantees for every variant. This overview answers three questions: what is CVA6, how does it process instructions, and where can you learn more? By the end, you should be able to distinguish a core from a system, read a configuration example, and identify the evidence needed for a capability claim. I created this community course for OpenHW Explorer, interpreting official documentation and project records. Detailed architecture and verification topics are left for later lessons.



## 2. The ISA, the community and the core implementation have different jobs (s02)

Place these names at different levels. RISC-V is an instruction-set architecture: it defines instructions and their software-visible behavior. OpenHW organizes collaboration around open hardware, and CORE-V is its portfolio of open cores and companion projects. CVA6 is one processor-core family implementing RISC-V. Following the diagram, parameters define a particular configuration; platform hardware and software then turn it into a system. CV64A6 evolved from Ariane, developed at ETH Zürich and the University of Bologna. RV32 was added later. The ISA, portfolio, core and development board therefore describe different objects. The Foundation and CORE-V naming courses provide more background on the organization and its terminology.



## 3. Start with the system task, then choose a configuration and platform (s03)

Start with the system task, rather than asking which name sounds most powerful. Embedded control needs a dedicated program and platform interfaces, memory and interrupts. ## 7. Caching, address translation and physical protection have different jobs (s07)

Separate three questions when software accesses memory. A cache holds reusable instructions or data, helping avoid repeated accesses to more distant storage. In a paged system, the MMU uses page tables to translate virtual addresses and check page permissions. PMP controls read, write and execute permissions for physical-address regions; its effect also depends on privilege mode and settings. Our RV64, Sv39 source example includes an MMU and eight PMP entries. Those describe different capabilities. Reusing a value may avoid another distant-memory access, while mapping and permissions remain separate questions. A cache hit does not establish that an access is permitted. The parallel comparison teaches responsibilities, rather than three fixed serial hardware checkpoints. Their presence and integration must still be checked in the selected configuration and system. Sv39 is one RV64 paging mode; Sv32 is an RV32 example, while Bare does not perform paged translation. PMP needs effective-privilege, entry-matching and setting checks. Its implementation count is not a conformance conclusion.
