# 认识 CVA6：架构、用途与工程证据

## 1. CVA6：面向不同系统的可配置 RISC-V 处理器 IP (s01)

如果你想了解一套可以阅读、修改并集成进自己系统的 RISC-V 处理器设计，CVA6 是一个具体的入口。它是一套可配置的开源处理器 IP，32 位与 64 位版本共享 SystemVerilog 源码。这里的 IP 是可复用的硬件设计：它执行指令，却还需要内存、外设和软件组成完整系统。你会看到它承担嵌入式控制、运行 Linux 和管理加速器等不同角色。不过，这些用途并不是对任意配置的保证。我们要把三个问题说清楚：它是什么，指令怎样在核中处理，以及怎样找到可信资料继续学习。学完后，你应能区分核与系统，读懂一个具体配置，并判断一条能力结论需要什么证据。这门概览课由我为 OpenHW Explorer 制作，依据官方文档和项目记录进行解释，属于社区原创课程。更深入的设计和验证细节，留到后续课程。



## 2. 指令标准、协作社区与处理器实现各有职责 (s02)

先把四个名称放在正确的位置。RISC-V 是指令集架构，定义程序可以使用的指令及其行为。OpenHW 是围绕开放硬件开展协作的社区组织，CORE-V 是它的开放核与配套项目组合。CVA6 是其中一套实现 RISC-V 的处理器核家族。沿着图向下，选定参数才得到具体配置，再把核与平台硬件和软件组合成系统。CV64A6 的来源是 ETH Zürich 与博洛尼亚大学的 Ariane，RV32 是后来加入的发展方向。因此，你不能把 ISA、项目组合、核和开发板互相替代。想进一步了解组织职责和命名，我们还有对应的两门课程。



## 3. 先看系统任务，再选配置与配套平台 (s03)

不要先问哪一个名字最强，先问系统要完成什么任务。嵌入式控制需要专用程序，以及平台提供的接口、存储和中断；GPIO、UART、SPI 等外设并不是 CVA6 核自动包含的功能。保护能力可以用 PMP 来理解：它控制物理地址访问，相关设置保存在专用 CSR 中。CSR 是更广泛的控制与状态寄存器类别，不能把它当作另一套独立内存保护单元。这里的 Linux 主机指常规分页系统，需要合适的特权模式、MMU 地址转换和启动软件，Cheshire 是具名平台入口。加速系统则需要管理软件与系统接口。CV-X-IF 是指令协处理器扩展接口；这一通用例子不能证明 Occamy 使用它。Occamy 展示的是 CVA6 管理核与独立 Snitch 加速器的分工。CVA6 SDK 与 FPGA 是开发入口，并不证明图中所有控制应用都已测试。无论 FPGA 原型还是 ASIC 集成，核配置、平台与软件都要共同匹配。下一页把这种匹配落实到参数。

- PMP 是访问保护机制，相关配置通过专用 CSR 设置；CSR 还承担其他控制与状态功能。
- 本页 Linux 讨论范围是常规分页系统。
- CV-X-IF 是指令协处理器扩展接口；本页不宣称 Occamy 采用它，Occamy 案例用于说明管理核与加速器分工。
- CVA6 SDK / FPGA 是开发入口，不代表所有列出的控制应用已验证。

## 4. 相同源码，通过参数形成不同能力组合 (s04)

这两列取自同一个固定源码快照。左边的 CV32A60X 是 32 位，只启用机器模式，没有 MMU，没有 F 和 D 浮点扩展，PMP 条目为零。右边的 RV64、Sv39 示例启用地址转换、三种特权模式和浮点扩展，并有八个 PMP 条目。M、S、U分别表示机器、监管者和用户模式，区分系统与程序运行的权限。它们说明，共用源码仍能形成不同能力组合。MMU决定地址转换能力，浮点扩展决定相应指令是否由该配置实现。二者是不同选择，不是一个“高级核”开关。你不需要记住这张表，而要学会问：我的软件需要什么，配置实际提供什么？下方探索还能查看一个双发射示例；发射宽度也不能直接当成实测性能。后面提到的 CV32A60X TRL5 是另一个具名发布范围，不要把它与这一页的源码示例混在一起。右列具体对应 cv64a6_imafdc_sv39，而不是全部 RV64 配置。零个 PMP 条目也不等于系统没有任何保护。同源不保证任意参数组合有效；这些是实现参数，完整 CSR 规范符合性还需另查。

- 右列是 core/include/cv64a6_imafdc_sv39_config_pkg.sv 在提交81245a4的示例，不代表所有RV64/Sv39配置；左列对应cv32a60x_config_pkg.sv。
- 同源不同参数不表示任意参数组合都有效或完成验证；缓存、接口与发射宽度仍要核对具体配置。
- 本页“发射宽度”图标是配置维度符号，不是性能数据；具名TRL5发布另有提交与范围。
- 零个PMP条目只表示该配置没有PMP条目，不等于整个系统没有任何保护机制。

## 5. 把架构读成一条指令通路和一组支持模块 (s05)

先沿上方的指令通路读图。前端选择取指地址，用分支预测帮助保持供给。译码识别操作和寄存器。发射检查操作数与执行资源是否就绪，记分牌跟踪处理中的指令与结果。执行处理整数运算、分支和访存，结果回到记分牌。浮点与协处理器接口按配置选择，不能把协处理器本体说成全部配置的内置模块。结果完成后，提交按程序顺序更新架构寄存器与 CSR，并协调相应存储和异常处理。核外平台提供内存、互连、中断、调试与外设。取指访问指令存储，Load/Store 发出数据请求；两种流量都会经过适用配置的存储支持和平台连接，调试并不是普通数据请求的目的地。图中缓存、地址转换和总线路径做了简化，交叉线没有连接点时也不表示相连。这是一张职责图，不是完整 RTL 接线图。历史六级流水线描述原始基线，框数既不代表级数，也不规定周期。下一页用两条指令看操作数等待与提交有什么区别。

- 这是职责图，不是完整RTL连接图，也不规定每一组职责对应一个周期或一级流水线。
- 执行结果回到记分牌，提交才按程序顺序更新架构寄存器、CSR，并处理相应存储/异常。
- Load/Store的数据请求通过配置相关的存储支持与系统互连；调试是独立平台功能。

## 6. 有了指令，还要等到它需要的数据就绪 (s06)

看这两条指令。lw x5, 0(x10) 从 x10 指向的地址读取一个三十二位字，准备产生新的 x5；add x6, x5, x7 用这个新值与 x7 相加。我们假设地址有效且按字对齐，内存值为十二，x7 已就绪且为三，没有异常或冲刷。译码能识别寄存器编号，却不能提供尚未返回的数据。add 需要 load 产生的新 x5，这是读后写依赖；即使整数单元空闲，也不能用旧 x5 代替。在这个 RV32 单发射基线例子中，记分牌跟踪就绪状态，并可将已返回的十二转发给 add。图中的 x5 等于十二首先表示可用操作数，不能据此断定架构寄存器已经更新。条件满足后 add 算出十五，两个完成结果都还要经过提交，正常按程序顺序退休后才得到最终 x5 为十二、x6 为十五。虚线区分 load 的结果路径，不表示退休可以跳过。网页状态表示概念事件，没有指定固定周期或转发提前窗口；缓存、总线等细节也被省略。请推进状态，观察结果可用与架构状态更新是两件不同的事。

- 这是RV32单发射基线的概念例，不规定固定周期，也不代表所有CVA6配置。地址有效且按字对齐，x7已经就绪，省略异常与冲刷。
- lw x5, 0(x10)读取一个32位字。12和3是本课教学假设，不是性能或实测数据；正常退休后x5=12、x6=15。
- add要用load产生的新x5，属于读后写（RAW）依赖。ALU空闲不能弥补缺少源操作数；记分牌跟踪就绪状态，并可转发已返回的值。
- 图中前往ALU的x5=12是可使用的新操作数，不表示架构寄存器此时已经更新。结果可以在退休前被转发，但不承诺每次都存在固定长度的提前窗口。
- load与add的完成结果都先进入等待提交的概念路径。Commit按程序顺序退休，才得到右侧最终架构状态；虚线仅用于区分load完成路径，不表示可选退休。
- 内存到LSU的箭头表示本例读回的数据；缓存、总线、记分牌存储细节在概念图中省略。结果路径不是完整物理接线图。

## 7. 缓存、地址转换和物理保护承担不同工作 (s07)

程序访问内存时，三个问题要分开。缓存保存可以复用的指令或数据，帮助减少重复访问更远的存储。MMU 在启用分页的系统中，按页表把虚拟地址转换为物理地址，同时涉及页权限检查。PMP 则对物理地址范围设置读、写、执行权限，其生效规则还与特权模式和配置有关。比如前面配置页的 RV64、Sv39 示例配置了 MMU，并有八个 PMP 条目；这两个数字描述不同能力。重复使用一个数据时，缓存可能避免再次访问更远的存储，但映射与权限仍然是不同问题。缓存命中也不意味着访问一定被允许。这里把三种职责并列，是为了帮助你判断配置表；并不是把它们画成三个固定串行的硬件关卡。有无这些能力以及怎样连接，都要回到具体配置和系统。Sv39 是 RV64 的一种分页模式，RV32 有 Sv32 的例子；Bare 不进行页式转换。PMP 要结合有效特权、匹配条目和设置判断，条目参数本身不是规范符合性结论。

- 缓存关注保存和复用指令或数据；缓存命中不会自动授予访问权限。此处不规定每次命中的具体检查时序。
- MMU的VA→PA与页权限说明针对启用分页的场景；Sv39是RV64中的一种分页模式，不代表全部CVA6。RV32的分页模式例子是Sv32，Bare模式不进行页式地址转换。
- PMP按物理地址范围定义读、写、执行权限，是否生效需看有效特权模式、条目匹配和相关设置；不能简化为所有模式无条件采用同一种规则。
- 这是并列职责对照，不是Cache→MMU→PMP的固定串行关卡；完整访存还涉及总线、物理属性等，此页不试图覆盖所有细节。
- 前页PMP条目8是提交81245a4具名源码配置的参数值，不能据此推出全家族条目数、配置已验证或完整v1.13规范符合性。实际架构CSR暴露、只读零槽位与实现参数应分开核对。

## 8. 运行软件，需要核、平台和启动资产共同匹配 (s08)

CVA6 执行指令，平台还要连接内存、中断、调试和外设。构建侧的工具链编译并链接程序，需要匹配 ISA、ABI 与平台；它不是运行时接力的一环。裸机、RTOS 与常规 Linux 所需配套不同。看固定 SDK 的 Genesys2 启动例：BootROM 加载后续程序，OpenSBI 提供机器模式服务，U-Boot 加载 Linux，内核启动用户空间。这表示控制交接，OpenSBI 会继续驻留；QEMU 路线跳过 U-Boot，也不是 CVA6 RTL 验证。图中 dts 是设备树源描述，内核通常接收编译后的 DTB。ext4 是一般根文件系统格式例子；这份 SDK 的 FIT 实际打包 u-boot.dtb 和 rootfs.cpio.gz 初始 Ramdisk，不能把图面 ext4 说成它的默认配置。SDK 测试列表中的完整标识是 cv32a6_ima_sv32_fpga 与 cv64a6_imafdc_sv39，来自维护方记录，本课没有重新启动实验。硬件图标和连线表示组成关系，DDR、AXI、PLIC、JTAG 等是配套举例，不保证每个实例都有。复制 Linux 镜像不足以证明新板卡支持；换参数或依赖后仍要核对全部匹配。

- 工具链用于构建二进制，不能当成运行时接力阶段；必须匹配ISA/ABI和具体平台。这里列GCC/LLVM/Binutils是一般工具举例，SDK具体构建依赖以固定README为准。
- 图中.dts表示设备树源描述；启动时通常由固件把编译后的二进制DTB交给内核。这份SDK的FIT模板实际打包u-boot.dtb。
- ext4是一般根文件系统格式例子，不能说成这份Genesys2 SDK的默认格式。固定SDK的FIT包含rootfs.cpio.gz初始ramdisk；README描述内核从Ramdisk启动用户空间。
- BootROM→OpenSBI→U-Boot→Linux→用户程序是SDK 267794d的Genesys2控制启动流程。OpenSBI驻留提供M模式服务，U-Boot在启动阶段工作；不是所有前一组件都会退出。QEMU例子跳过U-Boot，不是CVA6 RTL验证。
- SDK测试列表由维护方声明，标识是cv32a6_ima_sv32_fpga和cv64a6_imafdc_sv39；本课没有独立重新启动或验证这些配置。换板卡/参数/依赖仍须核对。
- 英语Use箭头表示软件使用启动资产；中文启动箭头表示资产支持软件启动，是同一依赖关系的两个表述，不是相反的控制流。平台初始化→程序、硬件横排连线均是组成/配套示意，不是完整实际接线或时序图。
- DDR/SDRAM、AXI、PLIC、JTAG和外设清单是一般配套举例，不保证每项在所有CVA6或Genesys2实例均存在。裸机/RTOS不一定需要Linux的设备树/根文件系统组合。
