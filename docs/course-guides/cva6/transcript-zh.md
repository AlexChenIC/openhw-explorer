# CVA6：能力、系统与工程证据

## 1. 怎样判断 CVA6 是否适合你的任务

假设团队正在为嵌入式控制器，或者 Linux 主机选择处理器。有人说，CVA6 支持这个需求。你接下来应该检查什么？CVA6 是一个可配置的 RISC-V 处理器家族，仅凭名字，还不能确定具体实现的指令集功能、存储系统和工程成熟度。这一课会带你对照三份真实配置，分析一段简单的执行过程，再把软件支持和应用案例与各自的证据对应起来。学完后，你应该能够写出这样的判断：哪个配置，用在什么系统中，目前有哪些结果可以支持这个选择。

## 2. 从指令进入内核，到架构状态更新

先从内核内部看起。前端取得指令，译码确定操作类型。发射逻辑检查操作数和执行资源是否就绪；记分牌跟踪已经发射的指令及其结果。接着，不同执行单元完成算术、分支或访存操作。提交阶段控制指令何时退休、结果何时更新架构状态，并处理异常。这些方框表达的是功能分工，不承诺每项工作固定占用几个时钟周期。要构成可用系统，内核外部还需要存储器、互连、中断、调试和启动软件。明确这个边界，才能判断一个问题应当在内核配置里解决，还是应当在外围平台中解决。

## 3. 对照三个具体配置

请依次选择三个配置，观察参数变化。在这份源码快照中，两种三十二位配置都没有开启内存管理单元、监督态和用户态，也没有开启原子与浮点扩展。它们的发射宽度不同：CV32A60X 有一个发射端口，CV32A65X 有两个。这里的六十四位示例则开启了所列出的应用处理功能。还要留意，提交宽度是另一个参数。配置构建逻辑会覆盖某些原始字段，例如为超标量配置设置两个提交端口。因此，应当把参数包和派生逻辑结合起来读。端口数量表示源码中的能力上限，实际吞吐率仍然取决于程序和各种停顿。

## 4. 区分发射、完成和退休

来看一条加载指令，后面跟着一条与它无关的加法。加载先发射，但存储器可能需要多个周期才能响应。如果操作数和资源都已就绪，后面的加法可以继续发射，并先返回结果。记分牌负责把结果对应到各自的指令。退休仍然保持程序顺序，因此，结果已经可用，与指令已经退休，是不同的状态。这就解释了为什么顺序发射和不同顺序的完成能够同时存在。判断性能也要保持这种区分：两个发射端口提供了宽度，但数据依赖、资源冲突、分支和访存延迟，决定了实际程序能利用多少。

## 5. 让内核配置与软件平台匹配

面向嵌入式任务，先检查软件移植层：指令集、调用约定、中断处理和板级支持，都必须与硬件匹配。一个具体例子是二零二六年六月八日发布的 ThreadX 版本，它增加了三十二位 CVA6 支持。版本标签里虽然含有二月，但实际发布日期是六月。面向 Linux 主机，则需要合适的内核能力，以及存储器、启动固件、操作系统内核和设备树的共同配合。CVA6 SDK 与独立维护的 Cheshire 平台，都是可以继续阅读的入口。无论走哪条路径，一项软件支持声明，都应当落实到兼容的平台和版本。

## 6. 理解不同验证方法各自检查什么

验证包含几类不同的工作。测试程序产生激励；测试平台和参考模型帮助比较预期与实际结果；覆盖率则回答计划中的场景和实现结构被测到了多少，还有哪些缺口。CVA6 的验证目录分别组织了板级支持、仿真、测试和回归脚本，并且明确选择目标配置与仿真工具。架构测试又有自己的范围，主要检查指令集规范要求的行为。ACT4 是相关框架，但其文档也明确要求额外的处理器验证。本课并没有宣称某个 CVA6 构建已经通过 ACT4 认证。看到绿色结果时，应该继续打开运行记录，确认究竟测了什么。

## 7. 准确解读 CV32A60X 的 TRL5 发布

来看一个明确的成熟度声明。二零二五年四月二十三日的发布，明确说明这是达到技术成熟度五级的 CV32A60X 配置。它的范围包括 OBI 接口、没有缓存、没有物理内存保护条目，以及关闭指令获取栅栏扩展。发布说明还列出了覆盖率和静态检查方面的改进。引用这个结果时，应当保留完整的适用范围。前面配置对照使用的是另一份源码快照；另一个分支上出现同名配置，并不自动继承这次发布的证据。如果你增加功能或改变系统集成，就要确定哪些部分需要重新验证。安全认证则有独立的评估过程和证据要求。

## 8. 练习把结论限定在证据范围内

现在试试四张证据卡片。每张卡片给出一项已报告的结果，以及两个可能的结论。请选择既保留有用信息，又符合原始范围的结论。架构测试通过、具名版本的成熟度发布、硅片上运行 Linux，以及安全保证论证，回答的是不同问题，不能互相替代。尤其是，增加某种安全机制，或者使用带有认证材料的操作系统，并不会自动认证一颗新的处理器或整个系统。选择后请阅读反馈。如果一项结论范围过大，应该追问缺少的目标、版本、环境或评估材料，同时保留已有证据真正能够支持的部分。

## 9. 从四个案例理解 CVA6 的系统角色

四个案例展示了不同的系统角色。TRISTAN 项目介绍了 Bosch 基于定制 CVA6 和加速功能的工业雷达与人工智能演示，未来集成和认证仍属于探索方向。Thales 将 ASTRAL 介绍为面向航天的实验性系统，组合多个 CVA6、OpenTitan 和向量加速。Basilisk 提供了另一类证据：它将 CVA6 与 Cheshire 集成，采用开放设计流程和一百三十纳米工艺，并公布了硅片测量与 Linux 演示。在 Occamy 中，CVA6 是能够运行 Linux 的管理核，多核计算加速器则使用 Snitch 集群。引用每个案例时，都应当同时说明处理器的角色，以及已经展示到什么阶段。

## 10. 把资料整理成可复现的评估记录

把刚才的阅读整理成一份简短评估记录。先写清配置和提交版本，再列出与任务有关的派生参数。补充平台、软件版本和已有测试结果，说明缺口，并选择一项能够影响决策的下一步实验。例如，控制器项目可以先检查目标开发板上的中断行为；Linux 主机项目可以先建立可复现的启动流程。路线图信息还需要保留日期。二零二六年七月十五日的路线图讨论了 CV64A60AX 验证和双核锁步集成工作。这能帮助你了解正在推进的工程方向；至于已经完成的能力，仍然需要相应的发布或实现证据。

## 11. 完成四个工程判断

接下来，请完成四个判断，选择能够从给定证据中成立的表述。即使第一次就答对，也请阅读解释。题目分别涉及发射宽度与性能、成熟度发布的范围、系统证据能否直接迁移，以及处理器在大型芯片中的角色。你不需要背下每一个参数，但要知道，在作出判断之前应当检查什么。如果还有疑问，可以回到配置对照或证据卡片，再重新尝试。最后的源码任务会使用同样的思路，把课堂里的判断落实到你自己能够追溯的文件和版本上。

## 12. 完成你的第一份源码评估记录

请从资料面板打开 CV32A65X 参数包，找到超标量开关和原始提交端口字段。接着打开配置构建文件，追踪两种宽度是怎样派生出来的。把最终数值和提交标识一起记下来，再补充一条关于目标系统的描述，以及你仍然需要的一项证据。这样，你就得到了一份简短、可复现的工程记录。然后根据缺失的结果，继续阅读验证、平台软件或应用资料。希望你保留的习惯是：一条有用的能力判断，能够说清具体配置、系统边界，以及其他人可以打开检查的证据。
